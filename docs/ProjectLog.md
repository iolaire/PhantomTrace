## Decisions

Format: ID, date, status (Accepted / Superseded), context, decision, consequences.

### D-001 (2026-11-11, Accepted): Platform scope is macOS 27.2.1 only
- Context: only that version can be tested.
- Decision: no support or compatibility code for other macOS versions or operating systems.
- Consequences: simpler code; `Package.swift` declares `.macOS("27.2.1")`.

### D-002 (2026-11-11, Accepted): Core library has no AppKit
- Decision: `PhantomTraceCore` imports Foundation only (Darwin/DiskArbitration/OSLog in `System/` adapters). UI lives outside Core.
- Consequences: Core logic is testable; system effects sit behind protocols.

### D-003 (2026-11-11, Accepted): Property-based library is swift-property-based, not SwiftCheck
- Context: `Package.swift` pins `swift-property-based` 2.0.1; older specs and docs say SwiftCheck.
- Decision: `Package.swift` is the source of truth; steering follows it.
- Consequences: scaffolding spec and checks that mention SwiftCheck need updating.

### D-004 (2026-11-11, Accepted): Single SafetyPolicy gate for all actions
- Decision: every `ProposedAction` is approved by `SafetyPolicy`; unknown state means deny.
- Consequences: UI/CLI never call signal or unmount adapters directly.

### D-005 (2026-11-11, Accepted): Hook enforces project log updates at commit time
- Context: pushes to `main` go through PRs, so a commit-time check covers all code.
- Decision: a commit hook blocks commits that change code or config without staging `docs/ProjectLog.md`; a steering rule says what to record.
- Consequences: small friction per commit; escape hatch is an `[skip-log]` marker in the commit message for trivial changes.

### D-006 (2026-11-11, Accepted): Three focused hooks plus the project-log hook
- Context: the hackathon rewards visible hook use, but too many hooks add friction. A separate lint hook and test hook would both fire on every commit.
- Decision: `lint-on-save` for per-file feedback, one `pre-commit-check` that runs `Scripts/lint-and-test.sh` (lint, then tests), and `kiro-gitignore-guard` for the rule that `.kiro/` must never be ignored. Hook logic lives in scripts under `Scripts/hooks/`. Rejected: a post-task test hook (duplicates the commit gate) and a Stop hook (runs every turn).
- Consequences: PreToolUse hooks see only commits the agent runs, not terminal commits. With `project-log-check`, three hooks fire on agent commits. SwiftLint must be installed (`brew install swiftlint`) or the commit gate blocks every agent commit. Revisit if the gate gets slow.

### D-007 (2026-11-11, Accepted): Detect the Kiro surface with a script, enforce it in the existing log hook
- Context: the hackathon write-up asks how Kiro IDE, CLI, Web, and Crew differed, so each work-log row names its surface. Typing it by hand is easy to forget or get wrong.
- Decision: `Scripts/kiro-surface.sh` detects the surface. Verified: Kiro IDE (`TERM_PROGRAM=kiro` in the agent shell, `VSCODE_IPC_HOOK` or `VSCODE_PID` in IDE hook processes). Best effort and unverified: Kiro CLI (a `kiro-cli` parent process). Web, Crew, and Mobile have no known markers, so the script reports Unknown and `PHANTOMTRACE_KIRO_SURFACE` overrides it. The existing `project-log-check` hook runs the script and blocks commits whose new work-log rows have a missing or invalid surface. It does not block on a mismatch with the detected value, because a commit may hold rows from earlier work on another surface. No new hook was added.
- Consequences: an agent adding a row runs `Scripts/kiro-surface.sh --details` first. Non-IDE surfaces need the override or manual entry until their markers are known; update the script when they are.

### D-008 (2026-11-11, Accepted): Real git hooks mirror the Kiro commit hooks
- Context: Kiro PreToolUse hooks only see commits the agent runs, so commits made by hand skipped the project-log, lint and test, and `.kiro` checks.
- Decision: tracked git hooks in `Scripts/git-hooks/` call the same scripts in `--git` mode. `pre-commit` runs the `.kiro` guard and lint plus tests (lint and tests only when a Swift, package, lint-config, or script file is staged). `commit-msg` runs the project-log check, because only that hook can read `[skip-log]`. Each clone enables them once with `Scripts/install-git-hooks.sh`, which sets `core.hooksPath`. The Kiro hooks stay.
- Consequences: an agent commit runs the checks twice, once per hook layer. Manual commits are covered. Lint and tests are skipped for docs-only commits. `git commit --no-verify` bypasses the git hooks; the git-workflow steering forbids it for the agent. Resolved by D-010: `swift test` now passes with only Command Line Tools installed.

### D-009 (2026-11-11, Accepted): Detect Kiro Web from its sandbox environment variables
- Context: D-007 found no verified markers for Kiro Web, so Web rows needed a manual override. The Kiro Web agent shell sets `AWS_SDK_UA_APP_ID=kiro-web` and `KIRO_CUSTOM_USER_AGENT=KiroWeb/<version>`.

### D-011 (2026-11-11, Accepted): Make look-and-feel art transparent by flood-filling the white background, not by color-keying
- Context: the generated base images are JPGs on white, and JPG has no alpha. Many have glow (ghosts) or smoke and halftone (padlocks), so a plain white-to-transparent key leaves fringes or erases the white interiors of objects.
- Decision: `Scripts/make-transparent-pngs.py` treats dark outline pixels as a barrier and flood-fills from the image border. Inside that background region it converts white to alpha and un-multiplies the color, so glow stays as soft alpha. Anything enclosed by an outline stays opaque, and the result is cropped to its content. Where an outline has gaps that let the fill leak into an object (the padlocks, where smoke overlaps the outline), `SEAL_RADIUS_OVERRIDES` thickens the outline for that image only. The default is off, because sealing everywhere fills see-through areas such as the broken chain loop and the CRT shadow hatching. Originals in `original/` are never modified; outputs go to `use/`. Python tooling runs from a git-ignored uv venv with dependencies pinned in `Scripts/requirements.txt`.
- Consequences: a new base image may need its own `SEAL_RADIUS_OVERRIDES` entry; check it on both black and white with `Scripts/make-proof-sheets.py`. The window frame is still opaque inside, so a content cutout or 9-slice is a follow-up. Outputs are full resolution (2 to 5 MB each); export 1x/2x sizes when they go into the asset catalog. The Python tooling is separate from the Swift package and adds no runtime dependency.

### D-013 (2026-11-11, Accepted): Split AppKit code into PhantomTraceUI and PhantomTraceApp, and share mocks through PhantomTraceTestSupport
- Context: an executable target cannot be imported by tests, and Core must stay free of AppKit (D-002). The core, UI and property test targets all need the same hand-written mocks.
- Decision: `PhantomTraceUI` is a library (views, window composition, sprite and font loading, dialogs) with its own `PhantomTraceUITests`. `PhantomTraceApp` is a thin executable (`AppDelegate`, `AppComposition` composition root, `AppQuitter`, `SystemClock`). `PhantomTraceTestSupport` is a test-only target (not a product) at `Tests/PhantomTraceTestSupport` holding the shared mocks, used by the core and property test targets.

### D-014 (2026-11-11, Accepted): ResolutionPipeline is an actor
- Context: the pipeline holds mutable state (the attempt history that gates `SIGKILL`, and in-flight stage runs) and is called from the coordinator and the CLI across tasks.
- Decision: `ResolutionPipeline` is declared `public actor` and conforms to `StageRunning`. Every adapter call (signals, quit, shell egress, unmount) goes through it, after `SafetyPolicy` approval, so the single choke point in D-004 is also the single owner of that state. Time comes from an injected clock, so tests never sleep.
- Consequences: calls are `async` and serialized, so two stages cannot interleave on one pipeline. No `@unchecked Sendable` is needed for the history.

### D-015 (2026-11-11, Accepted): lsof discovery falls back to `lsof +D` and `fuser -c`
- Context: the device-based `lsof` form can time out or return truncated output, and `lsof` only sees processes the current user may inspect.
- Decision: the primary scan is `lsof -F ... -- <mountpoint>`. On a timeout or truncated tail the engine runs `lsof +D` and `/usr/bin/fuser -c`, each limited to 15 s. A failure of either fallback is swallowed, not fatal. `fuser` knows only pids, so its findings become open-handle records on the mount point itself. A result that came from truncation or a fallback failure is marked `partial` with warnings.
- Consequences: more complete results on busy volumes, at the cost of a slower fallback path. `fuser` records carry no real file path. Partial results are shown to the user, never hidden (product principle: honest failure).

### D-016 (2026-11-11, Accepted): A partial or failed pre-unmount scan counts as a failure, not as "zero locks"
- Context: Clean Handoff unmounts only after a fresh scan reports zero locks. A partial scan with no records could be mistaken for a clean volume.
- Decision: in `ResolutionPipeline`, only a complete (`!partial`) successful scan with no locks allows the unmount. A partial or failed scan is reported as a timed-out scan with no locks verified, and no unmount is attempted. The same rule applies to the rescan after a stage: it verifies nothing unless it is complete.
- Consequences: a flaky or truncated scan blocks Eject until the user rescans. Safer than risking an unmount decision on incomplete data. Covered by `UnmountGatingPropertyTests` (Property 15).

### D-021 (2026-11-12, Accepted): Cancellation is a first-class outcome in Core, and disk-image lookup is async
- Context: an audit against the swift-expert concurrency guidance found cancellation swallowed in the pipeline (a cancelled stage kept signalling and then rescanned), a cancelled scan reported as `lsofUnavailable`, and a semaphore with `Task.detached` blocking the coordinator actor during `.dmg` resolution.
- Decision: add `PhantomTraceError.cancelled` (and `EgressFailure.cancelled`) and map `CancellationError` to it at the Core boundary; `execute` checks cancellation before each action and throws `CancellationError` from the grace wait and rescan; `MountResolving.resolve` and `MountTableProviding.mounts(forDiskImage:)` become `async` so `hdiutil` runs through `ProcessRunning` with no blocking. `LiveUnmounter` adds a provisional 60 s DiskArbitration timeout that fails without the `diskutil` fallback.
- Consequences: exhaustive switches over `PhantomTraceError` gained a case (error text split into `describeOperation` helpers for the complexity limit). The 60 s value is not in the spec and should be confirmed. A started unmount is still not cancellable.
